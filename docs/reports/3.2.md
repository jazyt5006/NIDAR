# 3.2: Layer 5, correction handling, revisions and live tag output

Evidence level of every result: **simulation** (synthetic data, simulated SLAM corrections) and **unit**. No Gazebo,
recorded-data or hardware results. All timings are from the dev laptop; the Pi 5 will be slower and has not been measured.

Spec sections read: "PART 9 — LAYER 5: SLAM CORRECTION HANDLING AND LIVE OUTPUT" (9.1-9.4) and

## Summary
- **FAIL (R3).** R1 PASS, R2 PASS, R3 FAIL; the incremental re-measure still fails for a whole-history correction.
- Layer 5 now stores every accepted observation in a pose-independent form. A correction event (history or
  frame_correction) or a registration update re-derives Layers 2 and 3 and rebuilds Layer 4 by replaying the
  original batches. Tags are re-derived, never patched: the result equals an offline run on the corrected poses
  (0.0 m difference).
- Survivor ids stay stable across rebuilds. A tag whose confirmed cell changes becomes UPDATED with a tag revision.
  Live output goes through the existing codec (snapshots every 5 s and on revision changes, rate-limited updates).

- Reading: a whole-history loop closure touches every track, so the incremental mode cannot help much. It helps
  only when the correction window is short. Even then it is 2x over budget, and it is not exact (R1 holds in 33/35
  comparisons), so the default stays `full`.
- The cost is about 5 ms per replayed observation, dominated by the Layer 4 replay. Each update re-fuses all items
  of the track and re-integrates the cell probabilities.
- Small stores do not save time, because evicted observations still held by tracks (up to 64 x 50) are replayed too.

## Ambiguities and how they were handled
- **SLAM correction API unknown (spec 9.3 forbids inventing one).** One `PoseCorrection` interface was used for both
  sources named in the task. The real adapter waits for Q S4.
- **Frame correction window.** Taken as written: [previous correction stamp, event stamp). Observations before the
  window keep their earlier correction.
- **"Affected" observations of a history event.** Every observation captured before the event stamp. Those without
  a corrected pose (outside the range, or bracketed by mixed revisions) get POSE_NOT_CORRECTED. So a partial history
  correction changes every older observation (inflated covariance), and the incremental mode gains nothing for it.
- **R1 with two corrections.** The offline run uses the corrected poses known at that moment (revision <= k),
  because comparing against later poses would not be the same input.
- **Layer 4 finding (not changed in 3.2).** In loop_closure s2 the simulated detector fired a false positive over the
  person, giving two observations of one body in one frame. That produces two tracks; every later observation is then
  ASSOCIATION_AMBIGUOUS, and both tracks go UNRELIABLE and time out, so the survivor ends with no tag. Without Layer 5
  the 0.3 m pose offset let a fresh track form after the closure. R1 shows the offline run behaves the same way, so
  this is Layer 4 behaviour.
- **Footprint refinement and floor removal (both OFF by default).** Footprint is re-run at re-derivation. Floor
  removal makes the Layer 1 point pose-dependent; the stored camera-frame point is kept, which is a limitation.
- **survivor_id, map_rev and reg_rev are sent as their low byte (u8 fields).** More than 256 published survivors
  would collide on the GCS.
- **No persistence.** A restart loses the store.
