# 3.4: Layer 4 replay / recompute performance (behaviour unchanged)

Evidence level: simulation stream (R3 bench: 6 survivors, 250 s, ~2600 detections), dev-laptop wall clock. No Pi numbers.
**Status: STOPPED EARLY at the user's request. Target (full recompute of 2000 stored <= 1.0 s) is NOT reliably met.**

## What was done (all passed gate P1: golden check 234 runs, 0 differences, after each step)
1. Profile (before): full recompute dominated by `fuse` (numpy 2x2 `inv`, 189k calls, ~57 % of 40 s profiled), `cell_probabilities` (17 %), `view_bins`, `stamps()`. Files: `3.4_profile_before.txt`, `_after1`, `_after2`.
2. `fuse` in scalar 2x2 arithmetic with per-observation cached R^-1 (`TrackObs.rinv`) - same formulas and summation order.
3. `cell_probabilities`: scalar `math.erf`, shared Phi at cell edges (bit-identical to the old code on 3000 random cases).
4. Lazy `Track.probs` (computed on first access) and cheap-criteria-first `confirmable`; lazy `SurvivorObservation.cell_probs` (Layer 3 field, computed on first access from copies of its inputs).
5. Cached `Track.stamps()`, distance-first check in `_merge`, `_dist` helper instead of `np.linalg.norm`.
6. Thread safety (task step 3): `RebuildJob` / `Layer5Pipeline.job_sink` / `complete_rebuild`. Snapshot on the pipeline thread, `job.run()` on any thread, atomic swap with replay of observations accepted meanwhile; stale jobs return False. Inline mode (no sink) uses the same code and is unchanged. Not optimised for speed; the snapshot costs one effective-pose resolution per stored observation.
Not done: incremental per-bin fusion sums, vectorised association, `PoseSample.failure()` caching (0.3 s of 2.4 s profiled), publish cost in the live path.
